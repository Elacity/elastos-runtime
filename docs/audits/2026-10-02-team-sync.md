## How we work (changed 2 October)

A PR merges into `develop` when all checks pass and an independent review from a different AI model family than its author has passed. Changes to the gateway, page security headers or frames must also pass the installed Home journey. As before, every isolation change carries a test for the refused case, and until step S2 is done no PR adds a public route, an approval type, or an app or provider permission without approval recorded in #173. Codex can request an independent review itself (`elastos-pr-review`). Irzhy moves from reviewing every PR first to the isolation design, the threat model, the hacked-Home test suite and review after merge. `main`, tags and releases stay with Anders.

The project board was cleaned on 2 October (83 PR cards removed, 17 missing issues added). Its auto-add setting puts PRs back (13 so far) until the setting is changed ([#122](https://github.com/Elacity/elastos-runtime/issues/122)).

## User data

Runtime-managed wallet keys are encrypted, but the Runtime keeps the key that decrypts them in the same data folder; the device key and the Recovery Kit archive key are plain files there. Passkeys protect sign-in, not these files. On a hosted Home such as the seed, the operator can therefore use these keys. [#209](https://github.com/Elacity/elastos-runtime/issues/209) tracks the fix and needs a design decision: a client the user controls that verifies signed code ([#211](https://github.com/Elacity/elastos-runtime/issues/211)), a confidential VM checked by attestation ([#212](https://github.com/Elacity/elastos-runtime/issues/212)), or both. [#210](https://github.com/Elacity/elastos-runtime/issues/210) covers key storage on self-hosted Homes. Until #209 is done, hosted accounts are non-private demo accounts without wallets (#174). Anders judges that hosted accounts hold no real users or value yet; no inventory has checked this.
