# Debugging Policy

Use this file for stable debugging guidance only. Do not use it as a running
work log.

## Workflow

1. Observe the failure with a concrete command, URL, or user journey.
2. Write the smallest falsifiable hypothesis.
3. Run one experiment that can prove or disprove that hypothesis.
4. Record the root cause in the issue, PR, or commit message once the fix is
   verified.

## Verification

- Prefer product-level smoke tests for Home, app launch, document sharing,
  pairing, and mobile/touch behavior.
- Prefer `RUSTFLAGS='-D warnings' cargo check ...` when touching runtime module
  boundaries.
- Prefer `node scripts/home-entropy-check.mjs` after UI, naming, routing, token,
  or ontology changes.
- Keep historical debugging transcripts out of active docs. Git history already
  preserves them.

## Where Debug Notes Belong

- Put temporary investigation notes in the active issue, PR, review comment, or
  untracked working note.
- Put release truth in `state.md` or `elastos/CHANGELOG.md`.
- Put active branch coordination in `TODAY.md`.
- Put durable architecture or operator guidance in the relevant `docs/` file.

## Provider Bridge Invariant

Provider request/response pipes must be cancellation-safe. If an HTTP caller
times out or disconnects after a provider request is written, the bridge must
still drain exactly one response line before the next request can read from the
provider. Otherwise a later request can consume a stale response from an earlier
request and cross-wire data across accounts, networks, or capsules.

## Browser Paste Investigation - 2026-05-24

### Observations
- Host URL-bar paste works, but paste inside the remote Browser rendering inserts the literal character `v`.
- The Browser app now grants clipboard permissions and intercepts Ctrl/Cmd+V at document capture, but the user still sees `v` in the remote page.
- Current paste implementation writes a Selkies clipboard payload and then synthesizes Ctrl+V over the data channel.

### Hypotheses
- H1: The Browser app never sees the Control modifier. Evidence against: local event-flow smoke intercepts Ctrl+V before ordinary key forwarding.
- H2: The iframe lacks clipboard permission. Evidence against: live Home iframe now has clipboard-read/write and URL paste works.
- H3: The Selkies clipboard/synthetic-key transport is the failing boundary. Evidence for: the remote page receives `v`, exactly what would happen if the synthetic modifier is not applied or clipboard command is ignored.

### Root Cause
The paste path depends on Selkies accepting a clipboard-write command and a synthetic Ctrl+V sequence. In practice that path degrades to a literal `v`, so paste must be Runtime/provider-mediated instead of datachannel key simulation.

### Fix Plan
Route host paste through the Browser Engine Provider as an explicit `paste_text` input command. The provider inserts text into the focused remote browser element using CDP `Input.insertText` and returns a typed input receipt.

### Verification
- `scripts/browser-selkies-control-service-smoke.sh` now posts `paste_text` to `/pages/:id/input` and verifies the fake CDP server receives `Input.insertText` with the exact pasted text.
- `node scripts/browser-display-mode-smoke.mjs` passes and checks paste remains Runtime/provider routed.
- `node scripts/browser-entropy-check.mjs` passes and checks paste is no longer simulated as remote Ctrl+V.
- `node scripts/home-entropy-check.mjs` passes and checks the Browser iframe has clipboard-read/write allow policy.
- Live Browser assets now serve `browser-20260524d`; existing old control sessions were shut down so newly opened Browser sessions load the provider paste handler.

## Passkey Registration Warning Investigation - 2026-05-24

### Observations
- Chrome warned during guest passkey creation that `authenticatorAttachment` had
  an unknown value and that `pubKeyCredParams` omitted one of the default
  algorithm identifiers, ES256 or RS256.
- Home only transforms WebAuthn binary fields client-side; the registration
  option object is generated by the Rust identity layer.

### Hypotheses
- H1: Home creates an invalid `authenticatorSelection` value. Evidence against:
  Home does not set `authenticatorSelection`.
- H2: The server serializes an unset optional field as `null`. Evidence for:
  `AuthenticatorSelection.authenticator_attachment` lacked
  `skip_serializing_if`.
- H3: The server advertises too narrow an algorithm set. Evidence for:
  registration options only included ES256.

### Root Cause
The server emitted WebAuthn creation options that were valid for some
authenticators but not browser-clean: an unset `authenticatorAttachment` was
serialized as `null`, and only ES256 was offered.

### Fix
Omit unset `authenticatorAttachment`, advertise ES256 and RS256, and accept
RS256 credentials by parsing/verifying RSA COSE keys in the identity layer.

### Verification
- `cargo test --manifest-path elastos/Cargo.toml -p elastos-identity --lib`
  passes in the active worktree.
- Public live endpoint
  `POST /api/auth/passkey/register/begin` returns `alg: -7` and `alg: -257`
  and omits `authenticatorAttachment` when unset.

## Hypotheses - 2026-05-26 Home Bell And ela.city Balance Regression

### H1: Home event fallback misses the first wallet request after SSE failure
- Supports: Home no longer polls summary; `handleHomeEventsPayload` suppresses shell-summary refresh when the client has no cursor and `broadcastInitial` is false. If SSE fails and long-poll fallback starts with an empty cursor, the first existing wallet request is accepted as baseline and the bell never refreshes.
- Conflicts: If SSE stays connected before the request is created, the server should emit `wallet.requests.changed`.
- Test: Simulate an initial Home events payload with a wallet event and no cursor; verify Home requests a summary refresh.

### H2: Wallet request creation succeeds but Home snapshot does not include it
- Supports: User reports request can be manually found/opened in Wallet or Inbox in earlier flows, but Home bell does not alert.
- Conflicts: `home_realtime_snapshot` calls `system_wallet_approvals_summary` and appends wallet approval notifications.
- Test: Gateway test creates a wallet approval, calls `/api/apps/home/events?wait_ms=0&cursor=<old>`, and asserts `wallet.requests.changed`, then `/api/apps/home/summary` includes the notification entry.

### H3: Browser exposes the wrong active EVM account to ela.city
- Supports: Browser default selection currently prioritizes `transaction_intent` defaults over any Browser-specific intent and projects EVM accounts across supported chains. A stale external or wrong default account can make ela.city see an address with no ESC balance.
- Conflicts: Recent current principal has an ESC transaction default pointing at a funded account.
- Test: Add a Browser bridge test with a funded ESC/browser default and a stale Ethereum transaction default; assert Browser chooses the explicit Browser/default ESC account.

### H4: ela.city keeps a stale connected wallet in site storage after Runtime account changes
- Supports: User previously observed ela.city auto-logging into an old wallet even after changing Wallet defaults. A dapp can cache a previously connected address in localStorage/cookies and keep querying its balance.
- Conflicts: `eth_accounts` should return the current Runtime account when the dapp asks again.
- Test: Verify Browser provider emits the current account consistently for `eth_accounts` and `eth_requestAccounts`, and document/implement a per-site reset or account-changed route if dapp cache remains stale.

## Experiments - 2026-05-26 Home Bell And ela.city Balance Regression

- H1 experiment: changed Home event handling so any first payload containing events triggers the same summary refresh path as later cursor changes. `node scripts/home-entropy-check.mjs` now asserts this invariant. Result: confirmed and fixed.
- H2 experiment: reran `test_home_events_long_poll_returns_cursor_and_keepalive` and `test_wallet_approval_journey_creates_request_reviews_in_inbox_and_signs`. Result: server-side Home summary and Inbox notifications include wallet approvals; the missing bell was client event fallback behavior, not summary composition.
- H3 experiment: changed Browser default selection to prefer explicit `browser_connect` before generic `transaction_intent`, and made Wallet EVM default updates mirror to `browser_connect`. Result: `browser_default_chain_prefers_browser_connect_when_present` and `test_wallet_transaction_default_also_drives_browser_connect_default` pass.
- Live deployment: built and installed a new gateway binary, copied Home assets as `home-20260526c`, restarted the live gateway on `127.0.0.1:8090`, and verified the public Home route serves `home-20260526c` with the fixed event condition.

## Root Cause - 2026-05-26 Home Bell And ela.city Balance Regression

The Home bell regression was caused by replacing frequent summary polling with event streams but suppressing the first actionable event payload when the SSE stream falls back to long-polling. The Browser balance regression risk was caused by Browser account selection not treating the Browser-connect account as the strongest Runtime wallet default.

## Fix - 2026-05-26 Home Bell And ela.city Balance Regression

Home now refreshes shell summary for wallet/inbox events even when they arrive in the first long-poll payload after SSE fallback. Wallet EVM default updates now also set a `browser_connect` default, and Browser uses that default before generic transaction defaults.

## External Provider Deploy Invariant

When code inside a standalone external provider changes, deployed Home or app
assets are not enough. Rebuild the provider binary, install it under the active
`XDG_DATA_HOME/elastos/bin`, update the provider entry in `components.json` with
the new sha256 and size, and restart the gateway so the provider process is
respawned. Otherwise Home/Library can serve current JavaScript while the running
provider still returns stale roots, operations, or schemas.
